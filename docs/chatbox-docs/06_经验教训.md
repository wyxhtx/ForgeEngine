## 编码类

- **现象**：.ps1 中文乱码 / bat 中文乱码
  **规则**：.ps1 = UTF-8 带 BOM；代码/.md = UTF-8 无 BOM；bat/txt = ANSI(GBK)
- **现象**：VS 输出窗 vcpkg 中文乱码（濮濓絽婀...）
  **根因**：vcpkg 输出 UTF-8，VS 按系统 GBK 解码
  **解决**：无（显示层问题）；命令行看正常
  **防御**：构建正常即可忽略，排查用命令行
- **现象**：VS 输出窗口里**自己写的**构建期工具（ForgeReflect）中文日志乱码成"鍙嶅皠鐢熸垚"，同一份日志里 CMake 写的 `反射生成：DescriptorConfig.gen.h` 却正常（注：该构建期工具 2026-09 已删，反射改运行期现算；转码这条经验对任何自研构建期工具仍适用）
  **根因**：工具用 std::cout 吐 UTF-8，而 VS/MSBuild 捕获子进程 stdout 时按**本地代码页**解码（.NET Framework 的 `Encoding.Default` = ACP = 936）；CMake 的 COMMENT 不走子进程 stdout（它是工程文件文本），所以两种中文命运不同
  **解决**：工具输出前转码：UTF-8 → 宽字符 → 目标代码页；目标页取 `GetConsoleOutputCP()`，为 0（无控制台 = VS/MSBuild 的 CreateNoWindow 管道）时取 `GetACP()`。实测无控制台路径吐 GBK 字节 `B7 B4 C9 E4 C9 FA B3 C9 A3 BA`（按 936 解码即"反射生成："），有控制台路径跟随控制台代码页（chcp 65001 时仍是 UTF-8）
  **防御**：①自研构建期工具凡输出中文都要走这个转码（`toOutputCode`），**别指望 `SetConsoleOutputCP`**——无控制台时它不生效，改了也白改 ②验证编码问题必须看**原始字节**（`ReadAllBytes` + 按目标代码页 `GetString`），用默认 UTF-8 读文件会得出错误结论（本次就先用旧 exe 验了一轮才排除）③第三方工具（vcpkg）的同类乱码只能忽略

## PowerShell / 执行类

- **现象**：PS7 里 [System.IO.File]::ReadAllText 相对路径去 system32 找
  **根因**：PS location 与 .NET CurrentDirectory 不同步
  **防御**：脚本内一律 Join-Path $PWD（绝对路径）
- **现象**：粘贴多行命令报 Get-Process / else 报错
  **根因**：复制内容混入历史提示符；交互式 if/else 分行
  **防御**：只复制代码块本体；if/else 写单行；整块一次粘贴勿逐行敲；命令块开头加 cls 清屏（07 协议）
- **现象**：占位符 <...> 被原样执行，覆盖文件
  **防御**：执行前确认无 < 占位符未替换
- **现象**：here-string 直接放方法参数 → ParserError
  **防御**：先存变量（$x = @'...'@）再传参
- **现象**：字符串 Replace 不命中（静默）
  **根因**：替换串空格数/全半角与原文不符
  **防御**：先 Select-String 原文核对再 Replace；先长后短

- **现象**：`$raw -replace [regex]::Escape('a' + $x + 'b'), 'c' + $y` → 报 "The -replace operator allows only two elements to follow it, not 4"
  **根因**：`-replace` 的右侧操作数按**参数模式**解析，空格分隔的表达式会被拆成多个数组元素（4 个）
  **解决/防御**：字面替换一律用 `$s.Replace($old, $new)`，且先把 `$old = '"' + $x + '"'` 算好再传；确需正则才用 `-replace`，两侧各先存变量

- **现象**：行级替换切坏 .ps1——用"行号定位起止+数组重组"替换 forgeEngineCmdList.ps1 的函数段，定位错位切掉文件大段，dot-source 报 ParserError（Unexpected token '}'）
  **根因**：函数结尾用"行首恰为 }"判定，文件内其他行首 } 干扰匹配；函数实际在文件末尾，行号假设错误
  **解决**：git checkout -- 文件恢复 HEAD 底稿 → 纯追加（ReadAllText + 末尾拼接 + WriteAllText 保 BOM/CRLF）重建
  **防御**：①向现有 .ps1 加函数一律"末尾纯追加"，禁止行级替换/数组重组 ②动手前 git ls-files 确认有底稿可回滚 ③验证文件干净先 Remove-Item function:xxx 清内存残留再 dot-source（否则旧函数仍在会话，Get-Command 误判未改干净）④加分区注释前先 Select-String '^# [一二三四五六七八九十]+、' 查已有编号（本次误写"三、"实为"七、"，撞"三、查看"）
- **现象**：手写解决方案 `build\ForgeEngine.slnx` 被"按关键词删行"的脚本改坏（留下孤立的 `<BuildDependency>` 与多余的第二个 `</Project>`）→ VS 打不开；同一轮里 `cmd\forgeEngineCmdList.ps1` 被无 BOM 编码写回，**BOM 丢失**
  **根因**：①按行过滤 XML 会拆散标签配对，而我只按"行数对不对"验收（20→15 就以为成功）②批量改写统一用了 `UTF8Encoding($false)`，没区分 `.ps1` 必须带 BOM
  **解决**：`build\ForgeEngine.slnx` 从 HEAD 还原（13 行，`[xml]` 解析通过、与 HEAD 逐行 0 差异、MSBuild 构建 exit 0）；`.ps1` 用 `UTF8Encoding($true)` 写回后自检 BOM/CRLF，并与 HEAD 逐行比对确认"只多了一行"
  **防御**：①改 XML / `.slnx` / `.vcxproj` 后**必须 `[xml](Get-Content -Raw)` 解析校验**，不能只看行数 ②凡改 `.ps1` 一律带 BOM 写回并自检 ③一切批量改动的验收 = **回读内容/结构**（逐行比对或解析），行数只作辅证 ④改工作区外文件（如库）前先看它的 EOL/BOM 约定，别套用别的目录的
- **现象**：脚本批量重排大文件（54 个结构体 / 3300+ 行）时把文件改坏（静默多插 759 行），另一版脚本静默丢内容
  **根因**：①`@(@('clear',3))` 这种"单元素嵌套数组"被 PowerShell 展平成 `@('clear',3)`，取 `$pair[0]`/`$pair[1]` 得到字符 'c'/'l'，模式变量变 `$null`，而 `-match $null` 匹配任意行 ⇒ 改到错误位置 ②函数块收集只看签名行、不配平括号/花括号（多行签名、`template<>`、单行体 `{ … }`、注释里的括号都会误判）⇒ 函数体被当"无法归类"或被丢弃 ③调整完"前置空行"后仍用**过期行号**去数"后置空行"，吃掉刚插入的行
  **解决**：内容先 `Copy-Item` 备份到 build\ 下；坏掉后用**只读** `git show :<path>` 从索引恢复（恢复后与索引逐字节一致）；脚本内置"每个单元非空行**内容多重集**不变"校验，任一单元不符就跳过不动它
  **防御**：①批量改结构/格式的脚本一律"默认干跑、`-Apply` 才落盘"，并打印逐单元变更清单 ②校验用**内容多重集**（非空行排序后取哈希）而不是行数——它同时抓得住丢失与重复 ③验收补一条**幂等性**：改完再干跑一次应报"0 变更"，否则说明规则没落全 ④别用 `@( @(a,b) )` 传多字段参数，改用具名字段（hashtable）或多条独立语句 ⑤内联 pwsh 命令里避免嵌套引号（`"$($x.Contains('y'))"` 会解析失败、整段不执行且无输出），先赋值给变量再拼接 ⑥别用 `| Select-Object -First N` 截断"会写盘"的脚本输出——`-First` 取够对象就**终止上游管道**，而写盘在脚本末尾 ⇒ 文件根本没写、脚本被半路掐断（本次 `-Apply` 就这样白跑一次，靠 mtime 未变才发现）；要截断先把输出存进变量再取 ⑦PowerShell 变量名**大小写不敏感**：`$D`（备份根路径）与 `$d`（循环变量）是同一个变量，本次曾因此把路径覆盖成 `03-种族`、还在工作区建出 3 个垃圾目录——路径类变量一律用多字符名（`$Root`/`$Dest`）


- **现象**：用 SendInput/PostMessage 向游戏窗口注入按键做"自动试玩"，脚本报"前景窗口不是游戏窗口"——`SetForegroundWindow` 被 Windows **前台锁**拒绝，输入实际发给了**别的前台窗口**：表现为"键发了但没生效"（视角不动/方块不破坏），还可能误操作到用户其它窗口
  **根因**：`SetForegroundWindow` 仅在"本进程已是前台"或"由前台进程调用"时生效，后台进程调用会被拒（只闪任务栏）
  **判据**：①只发"退出键"做对照——引擎不退出即证明注入没到达窗口 ②注入前后比对 `GetForegroundWindow()` 是否等于目标窗口 ③注入后看游戏侧硬证据（本次运行新增/修改的存档文件 mtime+字节）而非只看脚本打印
  **解决/防御**：激活顺序 `ShowWindow(hwnd, SW_RESTORE)` → `AttachThreadInput(GetWindowThreadProcessId(GetForegroundWindow()), GetCurrentThreadId(), true)` → `SetForegroundWindow(hwnd)`（用完再 `AttachThreadInput(..., false)`）；或先 `SetCursorPos` 到客户区点一下激活；输入前**一律断言"前台窗口 == 目标窗口"，不满足就不发**（本机实测：`GetWindowThreadProcessId` 按 PID 找窗口可行，但前台切换可失败）
- **流程约定**：凡需要**人工操作**的验证（窗口/焦点/resize/试玩），**默认直接请用户执行**，不自行上自动化；自动化只在用户明确要求时做，并作为**备用件**保留（如 `cmd\play-test.ps1`）

- **现象**：`@('…','a' + $today + 'b','…')` 本该拼成一个字符串，结果数组里多出好几个元素（标题被拆成 3 行）
  **根因**：PowerShell 里**逗号 `,` 的优先级高于 `+`**，数组字面量内的 `+` 拼接会被逗号切开
  **解决/防御**：先把拼好的字符串放进变量再塞进数组，或在数组里给拼接套括号 `( 'a' + $b + 'c' )`
- **现象**：`foreach ($l in $L) { … }` 之后 `$L.Count` 变成 1（集合被“吃掉”），还误判成“文件被并成一行”
  **根因**：**PowerShell 变量名大小写不敏感**，循环变量 `$l` 与集合 `$L` 是同一个变量 ⇒ 循环把它们互相覆盖
  **解决/防御**：集合变量与循环变量**取明显不同的名字**（`$lines` / `$ln`）；同理别用 `$i` 与 `$I` 之类只差大小写的名字
- **现象**：Node 脚本写回文件时写成 `Buffer.concat(list, Buffer.from(text, "utf8"))` ⇒ 文件被写成 **0 字节**（本次连写坏两个源文件 `VkStruct.h`、`VkList.h`；此前同法写坏过探针 `gen-equiv.ps1`）
  **根因**：`Buffer.concat(list, totalLength)` 的**第二个参数是总长度（number）**，误传 Buffer 时；`list` 非空 ⇒ 抛 `ERR_INVALID_ARG_TYPE`，`list` 为空（无 BOM 文件）⇒ Node **提前返回空 Buffer**，于是"静默写 0 字节"，脚本继续往下跑
  **解决/防御**：①写回封装里**不用 `Buffer.concat`**，直接字符串拼 BOM：`writeFileSync(p, (bom ? "\uFEFF" : "") + text, "utf8")` ②`save()` 写完**立刻读回断言字节数**（`readFileSync(p).length !== 0` 且 `=== Buffer.byteLength(text)`）③`load()` 里备份加 `existsSync` 守卫，避免重跑时用好文件覆盖掉好备份（本次靠脚本开头备份的 `.uiText连线前.bak` 恢复）
- **现象**：P3 把 `sVertexs/dVertexs` 改成 `sMesh/dMesh` 时，我用来找调用点的 grep 模式写成 `vertexs|indexs|tVertexs|sVertexs|dVertexs`——**漏了索引侧的 `sIndexs`/`dIndexs`**，4 处绘制调用的"索引个数"没改，靠编译器 `C2039/C2065` 才兜住（若漏的是"值"而不是"名字"，编译器不会报）
  **根因**：改名要扫的是"同一概念的全部命名变体"，而我只按记得住的几个写了模式；`顶点/索引 × 静态/动态/地形` 的组合是 6 个名字，模式里只覆盖了 4 个
  **解决/防御**：①扫描模式按**变体矩阵**枚举（`(t|s|d)?(Vertexs|Indexs)`、`xxxVertex::(vertexs|indexs)`），或用 `-Include` 全树 + 两个词根分别扫 ②**拿编译当兜底**（本项目闸门第一步就是编译，名字类漏改必然报）③替换脚本的每个断言都要写**准确的命中次数**：本次两次靠"次数不符即停"挡住了误改（`indexs.push_back` 实际 5 处、`[threadId]` 阴影上传实际 2 处）
- **现象**：改审计输出格式的脚本里，先在开头取了一次 `lines = t.split("\n")` 快照，中途又用同一份**旧快照**做行级插入、最后 `t = lines.join("\n")` 回写 ⇒ 把两次替换（结构体加成员、列数 17→16）**静默回滚**，只留下行级那一步；编译报 `name 不是成员` 才发现
  **根因**：`lines` 与 `t` 是两个副本，替换只改 `t`；用旧 `lines` 回写等于用修改前的文本整体覆盖 `t`
  **解决/防御**：①**单快照**：要么全程只改 `lines` 且最后只 `join` 一次，要么每次替换后**重新取快照**（本次改成单快照后一次通过）②行级插入与字符串替换**别混用**两种副本 ③每步替换都带命中数断言，并在写盘后立刻**回读校验关键行**（本次回读校验立刻暴露了 `columnCount` 仍是 17）
## CMake / 构建类

- **现象**：CMakePresets.json 加 // 注释 → JSON Parse Error
  **根因**：preset 解析不接受注释（实测）
  **防御**：preset 保持严格 JSON；说明写文档
- **现象**：目录改名后 cmake 报 CMakeCache 路径不匹配
  **根因**：cache 固化旧绝对路径
  **解决**：fe-clean（删 build\vs，保留 vcpkg_installed）→ 重配
- **现象**：ForgeEngine.dir / x64 / Debug 等空目录与中间目录
  **根因**：VS 生成器硬编码（IntDir 不可配）
  **防御**：接受；exe 已收 bin\output
- **现象**：VS 出现 "CMake Rules" 节点
  **根因**：自定义规则输出文件（spv）进了 target_sources
  **解决**：assets GLOB 排除 shader\（规则产物）
- **现象**：exe 输出目录写死绝对路径
  **根因**：CMAKE_BINARY_DIR 展开（CMake 设计）
  **防御**：别手动改 vcxproj，改 CMakeLists 的 RUNTIME_OUTPUT_DIRECTORY
- **现象**：想自定义 "Fast" 配置档 → vcpkg 失败
  **根因**：vcpkg 只认内置配置名（非标准配置转储/链接错库）
  **防御**：不自定义新配置名；用内置 RelWithDebInfo 重定义 flags（现配置集 Debug;Release;RelWithDebInfo，RelWithDebInfo=/DNDEBUG /Od /Zi 快速日常档，带 PDB 可断点）
- **现象**：单 TU Release /O2 全量 ~12.4s（/d1reportTime：前端 ~2.8s、后端 ~9.6s）；/cgthreads8 无效
  **决策**：日常用 RelWithDebInfo（~6s）；Release 仅发布/优化验证跑 → 现阶段不拆 TU
  **根因**：全 inline 头设计 → codegen 锚定调用点（main→Pipeline::drawFrame/ctor→Plate/Buffer/3 worker 全链）；"世界/初始化/帧/工具"4 路均分需所有权解耦（Plate 移出 Pipeline）+ namespace 全局 inline 化（VkInfo.h engineInfo/lockInfo/getLock 等 LNK2005 风险），现实上限 ~6-7s
  **防御**：复评触发 = 全量 >20s 或频繁改头文件痛感明显；届时先做 Pipeline 方法定义下沉 graphic\Pipeline.cpp（声明留类内）→ 再做 Plate 解耦；任何多 TU 前先 C0：namespace 级非 inline 全局改 inline
- **现象**：想让 VS 的中间目录跟手写工程一样落到 bin\intermediate\x64\<Config>（obj / pch / pdb / tlog / recipe 一并），但 CMake 生成的 vcxproj 里 <IntDir> 写死为 <Target>.dir\<Config>
  **根因**：CMake 的 VS 生成器没有 IntDir 配置项；VS_GLOBAL_IntDir 写在 Globals 属性组（先于逐配置属性组）会被覆盖。另有两处不吃 $(IntDir)：① DesktopDeployRecipeFile 由 Microsoft.CppBuild.targets:37 在**评估期**用当时的 IntDir 定死默认值 ② CMake 给 cmake_pch.cxx 写的 PrecompiledHeaderOutputFile 是**绝对路径**，元数据评估期固化
  **解决**：config\cmake\ForgeIntermediate.targets（源）+ CMakeLists 的 configure_file(... ${CMAKE_BINARY_DIR}/Directory.Build.targets COPYONLY)。该文件由 MSBuild 在工程**末尾**导入：PropertyGroup 里重赋 IntDir 与 DesktopDeployRecipeFile；再用 <Target BeforeTargets="ClCompile"> 内不带 Include 的 <ClCompile>（= 改全部现有项）改写 PrecompiledHeaderOutputFile 元数据。实测 Main.obj / cmake_pch.pch / vc145.pdb / recipe / tlog 全部落到 build\vs\bin\intermediate\x64\Release\，build exit=0
  **防御**：①只覆盖主目标（Condition="'$(MSBuildProjectName)'=='ForgeEngine'"）——多工程共用同一 IntDir 会触发 MSB8028 ②Directory.Build.targets 属 MSBuild 侧覆盖，CMake 不知道（vcxproj 里 IntDir 原样），别去手改生成的 vcxproj ③ForgeEngine.dir\ 等空壳目录会被生成器每次 configure 重建（0 文件），无法消除 ④用 configure_file（不是 file(COPY)）源变更才会自动重配 ⑤改完必须重新 configure + 实编，不能只看 vcxproj 文本 ⑥同类残留要一次查完：辅助工程的默认 IntDir `$(Platform)\$(Configuration)\$(ProjectName)` 与默认 OutDir `$(SolutionDir)$(Platform)\$(Configuration)\` 会留下 `build\vs\x64\`；ForgeEngine 的 `<ImportLibrary>…\build\vs\<Config>\ForgeEngine.lib`（EXE 用不到 import lib）会被 `Microsoft.CppBuild.targets:1450` 按 `%(Link.ImportLibrary)` 建目录，留下空的 `Release\` / `RelWithDebInfo\` —— 两者都在同一 targets 文件里改指 `bin\intermediate` 即可（辅助工程各自子目录，避免 MSB8028），改完只剩生成器创建的 `<target>.dir\` 空壳

- **现象**：构建期生成的源文件（如反射生成的 `DescriptorConfig.gen.h`）改了内容，引擎却不重编；用 `| Select-Object -First N` 过滤构建输出后，下次构建报 MSB6003 `文件"…\CMAKE_PCH.PCH"正由另一进程使用`（注：该生成头 2026-09 已取消，教训对"任何构建期生成物"仍适用）

## AI 协作 / 文档类

- **现象**：AI 消息外层 ``` 内又嵌 ```（md 代码块）→ 消息截成三段
  **根因**：代码围栏嵌套冲突，Markdown 提前闭合

## dsh 试点类

- **试点结论**：dsh（DeepSeek Harness 0.1.2-rc）作为 ForgeEngine 执行体试点判定：方案 C（Chatbox 大脑 + dsh 执行体）成立
  **实测事实**：pwsh 持久会话；fe- 指令跨会话可用（免 dot-source）；只读命令零审批；中文读写无乱码（后续 2026-09-23：Chatbox 弃用，改 dsh 单轨，见 08_工作流.md）
  **环境约定**：DSH_HOME=E:\tool\app\dsHarness；Node v24.20.0（E:\tool\app\node）；npm cache 在 E 盘
  **关键坑**：Windows 下 .NET SetEnvironmentVariable 不广播 WM_SETTINGCHANGE，装完 node 后新终端 PATH 不生效；需重启或手动补 PATH
- **现象**：DSH 会话里 `cmake --preset vs` 或触发 ZERO_CHECK 重新生成时配置失败——`-- Running vcpkg install` → `write_contents_and_dirs("E:\tool\app\vcpkg\buildtrees\0.vcpkg_dep_info.cmake"): permission denied` → `CMake Error at vcpkg.cmake:953 (message): vcpkg install failed` → MSB8066；同一命令在 VS / 普通终端正常
  **根因**：DSH 文件沙箱（workspace-write）只允许写会话工作区，而 vcpkg 必须写工作区外的 `$VCPKG_ROOT\buildtrees`；报错由 vcpkg 自己打印，没有 harness 的 `[sandbox: file access denied]` 标记，易误判为 CMakeLists 语法错
  **解决**：配置/重新生成在 VS 或普通终端执行；确需在 DSH 里跑就对该命令一次性放宽到 danger-full-access（需审批；每次 configure 都要，因为 vcpkg 每次都写 buildtrees）。**策略放开（danger-full-access）后这些拦截会消失，但"重配"本身仍有风险（会重写 `CMakeCache.txt` 与编译器探测文件）⇒ 确需重配先备份 `build\vs\CMakeCache.txt`**

## Device vs VkDevice 包装类型坑（2026-09-29）

**现象**：把 `procDesc` 从 `procPipelineNode` 移到 `Buffer` 时，连续 5 次编译报
`C2665 procDescNode 没有重载可转换所有参数`（后来在构造体里调用时显示为 `C2664 无法将参数 1 从 Device 转换为 const VkDevice&`）。

**根因**：`Buffer(Device& tDevice, …)` 的形参是引擎**包装类 `Device`**，而 `create(const VkDevice&, …)` 要的是 **`VkDevice`** ⇒ 必须传 **`tDevice.device`**。

**教训**：
1. 引擎里凡 `Xxx(Device&)` 的成员调用 Vulkan API，一律用 **`.device`**（本仓 `Device` 是包装，不是句柄）。
2. 连续多次同一条 `C2665/C2664` 报错时，先怀疑**包装类型 vs 原生句柄**，不要去调作用域/花括号初始化——这次我因此白试了 4 轮。

### 1. 大改必须自愈：备份 → 锚点写入 → 编译失败自动回退
- **现象**：一次改 5 处（`cmdNode` 批原语＋状态机）后，编译过了但真跑卡死（ExitCode `-1073741510`），只能手工回退。
- **对策**：每个将改文件先备份 `build\temp\bak\<文件>.<意图>前-<日期>`；写入后先做括号平衡自检再编译；**编译失败 ⇒ 脚本自动回退**（不手工缝补）；通过再跑三闸门。今天两次误插、一次命名不符都是这样自动兜住的。

### 2. 锚点必须带「形状 + 越界」校验
- **现象**：按行号 splice 时漏删/多删一行（生成头多出一个 `};`），或插到了函数体之外（`cacheFile`/`ktxTexture` 不在作用域）。
- **对策**：写入前断言 ①目标行内容匹配 ②插入点 < 下一个函数头行号 ③花括号平衡 == 0；任一不满足 ⇒ **不写盘**。

### 3. 并行编辑纪律：改前先读「当前文本」
- **现象**：用户手工改过（`storeNode→spvDataNode`、`textureCacheSwitch→ktxCacheSwitch`、`loadKtx/uploadKtx` 私有化）之后，脚本仍按旧文本匹配 ⇒ 未命中或插错位置。
- **对策**：任何片段改动前**先读该片段**；命名以用户当前代码为准；改名后同步四处（探针桩与正则 / `docs\chatbox-docs` / 库《代码规范》 / `AGENTS.md`）。

### 4. `DeflateZstd` 顺序铁律：先上传 → 后压缩 → 再写盘
- **根因**：`ktxTexture2_DeflateZstd` 会把内存里的块数据压掉，先压就无法再上传。
- **收益**：BC7 69.34 MB → 25.19 MB（无损、`KTX_SS_ZSTD`），命中路径零转码（模型加载段 793 → 128 ms）。

### 5. 工作线程不得调 `Log::printError`
- **根因**：`printError` 打印后 `while(true);` 挂起 ⇒ 工作线程挂死无法回收。
- **对策**：纯 CPU 段（`loadKtx`）把错误装进 `ktxLoadNode::error`，回主线程再 `printError`；Vulkan 调用（`uploadKtx`）一律留主线程。

### 6. 相对路径缓存 = 随进程工作目录（会出现「两份」）
- **现象**：`storage/local/cache/ktx/` 随 cwd：闸门脚本 `-WorkingDirectory <exe目录>` ⇒ 落输出目录；从仓库根跑 ⇒ 落仓库根 ⇒ 两份各 ~25 MB。
- **对策**：接受现状（与 `pipeline.bin` 同机制）；要「只留一份」就统一启动工作目录，或手动清另一份。

### 7. 探针是「源码文本解析」⇒ 改名必须同步它
- **现象**：`descNode::create` 改名 `createReflectConfig` 后，探针正则仍抓 `.create(` ⇒ 抓到 0 条直接 `throw`（**闸门静默失灵**，我漏跑了探针才没当场发现）。

## MSDF 图集落盘缓存：冷 12.4 s → 热 14.7 ms（2026-10-01）
- **动机**：冷启动 ≈ 16.4 s，其中 **MSDF 烘焙 12.4～14.1 s（占 76～86%）**，大头是 `generator.generate()`（MTSDF 栅格化 3595 个字形到 2048²）。**坑：旧代码把「图集」日志打在 `packer.getDimensions` 之后、生成之前**，日志看着 2 s 就"烘焙完了"，实际耗时全在后面 ⇒ **计时打点必须覆盖到度量表填完**，否则必然误判（本轮就先误判了一轮，据此得出的"2.7 s 冷启动"是错的）。
- **做法**：图集结点构造时先算**缓存指纹**（魔数 `FEATLAS1`（末位＝格式版本）＋ 字体 size/mtime ＋ 字集表字节 ＋ `emSize`/`cornerAngle`/`pixelRange`/`miterLimit`，FNV-1a 64）；命中则直接读回「像素 ＋ 字形度量」，**连 FreeType 都不初始化**；未命中才烘焙，烘焙完**先写 `*.tmp` 再改名**（Windows 改名不覆盖已存在目标 ⇒ 先删旧件）。落点 `storage/local/cache/msdf/<字体名>.msdf.bin`（16.9 MB），开关 `engineInfo::msdfCacheSwitch`。
- **实测（RelWithDebInfo，RTX 3060 Laptop）**：冷 16.4 s（烘焙 12446 ms、写缓存后 16921052 B）→ 热 **2.7 s（缓存命中 14.69 ms，读 16.9 MB ≈ 1.15 GB/s）**；篡改缓存头 1 字节 ⇒ 日志"缓存已失效，重新烘焙"、重烘并**自愈回原指纹**；命中时不打 `uiText 字集`（跳过解析字集表）属预期。
- **防御**：①缓存只当加速用：任何读失败/内容不完整一律 `return false` 回落烘焙，**坏缓存不许让启动失败** ②失效判据宁多勿少——新增烘焙参数必须一并 `mix` 进指纹，否则"改了参数却复用旧图集" ③格式版本写进魔数末位，改磁盘布局就 +1 ④别用 `printError` 报缓存问题（它 `while(true)` 挂起），一律 `printWarning`。
## 排序工具「创建族」判据收紧：私有 create* 不入创建族（2026-10-01）
- **背景**：`reformat-structs2.ps1` 的条件②（名字以 create/recreate/clear 开头 + 全部调用者都是构造/① 生命周期入口 ⇒ Grp1 创建族）会把**私有**的 `createCharset`/`createFingerprint` 也提到私有段最前，跨组还多 2 行空行。
- **规则B（2026-10-01 定）**：私有段的 `create*/recreate*/clear*` = 无外部引用的纯内部辅助 ⇒ 一律 Grp2（留在其余私有、按调用顺序）；公开/保护段仍按条件② 判。实现：`SegAccess(label,isClass)`（无标签段按类型默认：class=private / struct=public）+ ②候选与「无构造函数」兜底两处都 `if ($it.Access -eq 'private') { continue }`。

- **注意**：struct 排序键末位是「**原位**」(`:629`)，所以把函数手工摆到目标位置后工具会保持不动（幂等）；但**不摆**的话工具不会主动帮你挪到「调用顺序位」，只会合并分组（差 2 行空行）。
## 规则C：struct 的私有段也按调用层级分组（2026-10-01）
- **口径（用户拍板）**：① 入口 = **构造族 ＋ 公开/保护段的函数项**（不是只构造族 —— 否则 `build`/`addValue` 这类对外入口的调用链会全判「不可达」而被塞到末尾）；② **跨层 3 空行**（与 class 一致）；③ 成对（get/set 同 Base）与同后缀家族**先行捆绑**、不被分层拆散；④ **只 struct 的私有段**，其余段仍「成对优先 + 原位」。
- **实现**（`cmd\reformat-structs2.ps1`）：`$hasPrivateSeg` 决定 struct 是否跑分层；`$isEntry = Grp0 -or (struct 且 Access≠private)`；段内 `$isLayeredSeg = IsClass -or (SegAccess=private)` 同时控制**家族门**与**层分量清零门**；BFS 后加一段「成对族同层同 Ord」的归并（否则两半被不同层调用会被拆开）。
- **实测影响面**：对 `VkStruct.h` 干跑，需重排 10（基线）→ **13**：`msdfGlyphAtlasNode`(+2，本次只落这一个) 之外还有 `swapSupportNode`、`cmdNode`、`pipeConfigNode`（纯重排、行数不变）——**规则C 是全 struct 生效的，只是本次按用户要求只应用一个 struct**。
- **注意**：apply 后工具干跑 `msdfGlyphAtlasNode` 已消失 ⇒ 幂等；层内次序仍由 `OwnCalls` 的**首次出现顺序**（EOrd）决定，所以同一层里「谁先被调用」看的是调用点在源码中的先后（例如 `getAtlasText` 因在命中分支的日志里先出现而排在 `createCharset` 之前）。

## DX12 层起步：Present 不在命令队列 fence 覆盖内（2026-10-01）
- **背景**：新开 `src\code\dx\`（独立 target `ForgeDx`，与 ForgeEngine 并存）：GLFW 建窗 + D3D12 设备/交换链/PSO（`SV_VertexID` 生成顶点，无顶点缓冲）+ 控制台每秒帧率；着色器走构建期 `dxc.exe`（HLSL → `.cso`，同 spv 的"每机现编不入库"范式）。
- **踩坑（关窗必崩，退出码 2173）**：挂 D3D12 调试层时，进程在 `swapchain.Reset()` 处以 `0x87D` 终止。VEH 里倒出 `ID3D12InfoQueue` 的存量消息才看到真因：`ID3D12Resource3::<final-release>: CORRUPTION: … is referenced by GPU operations in-flight on Command Queue …`。
  **根因**：**Present 才是本命令队列上最后一个「在飞」操作，而 fence 的 `Signal` 排在 Present 之前 ⇒ fence 等待天然盖不住呈现**；交换链释放时后备缓冲的最后一次引用仍被在飞呈现持有。
  **已排除**：`DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT` + `SetMaximumFrameLatency(1)` + 等可等待对象（无效）；关 break-on-severity（无效，走的不是那条路径）；关 DXGI 调试工厂（无效，出事的只有 D3D12 调试层）。
- **正解**：收尾时补一次 `Present(0, 0)` 把呈现推进，**紧跟一个新 `Signal`**，再等这个新值 ⇒ 呈现确实完成后才释放交换链。修后 exit 0、调试层 0 报错、收尾各阶段干净。
- **调试手法沉淀**：①在 VEH（`AddVectoredExceptionHandler`）里倒 `ID3D12InfoQueue` 的存量消息 —— 能拿到"进程临死前"的那条调试层消息（普通 drain 来不及）②`0x40010006`(OutputDebugString) / `0x406D1388`(MS_VC_EXCEPTION) 属噪声，直接跳过 ③调试层默认「CORRUPTION 即中断」在未挂调试器时会直接杀进程，`SetBreakOnSeverity(..., FALSE)` 可改为只记录、由自己的汇总打印并体现到退出码。
- **接线三坑**：①`src\code\**` 的源码 GLOB 会把带 `main` 的新层收进 ForgeEngine ⇒ 必须 `list(FILTER FORGE_SOURCES EXCLUDE REGEX "/src/code/dx/")` ②`Directory.Build.targets` 会把**非 ForgeEngine 工程**的 `OutDir` 也改到中间目录 ⇒ 新 exe 工程要排除出通用分支，否则 `Link.OutputFile` 与 `TargetPath` 不一致报 **MSB8012** ③ForgeEngine 的 `/MT` 是**逐 target** 设的 ⇒ 新 target 必须补 `MSVC_RUNTIME_LIBRARY`，否则与 vcpkg 静态库冲突报 **LNK4098**。
## dx 层渲染 forge 网格：四条 D3D12/VS 坑（2026-10-01）
- **背景**：按分层契约「forge 提供数据、dx 负责渲染」以**临时快照**打通：引擎启动时导出 `build\temp\work\forge-mesh.bin`（`vk\tool\MeshSnapshot.hpp`，临时件），dx 读快照建顶点/索引缓冲 + 深度 + 根 CBV + 相机，渲染 Layer_0（540496 顶点 / 810744 索引，快照 86.5 MB）。
- **坑 1｜`VS_TOOL_OVERRIDE` 是「目录级」源文件属性**：为让 ForgeEngine 工程树也显示 dx，把 `src\code\dx\*.cpp` 挂给 ForgeEngine 并钉成 `None` ⇒ **ForgeDx 里同一个 `Main.cpp` 也变成 `None`**，编不出 `main`，链接报 `LNK2019: 无法解析的外部符号 main`。⇒ 头文件与 `.hlsl` 可以两个工程都挂（属性一致即可），**`.cpp` 只能归真正编译它的工程**。
- **坑 2｜`.hlsl` 挂进 VS 工程必须显式钉 `None`**：VS 默认按 `FxCompile` 处理，会被 FXC 抢去编译并报 `error X3501: 'main': entrypoint not found`（本项目入口是 `VSMain`/`PSMain`，且由 dxc 编译）。
- **坑 3｜根签名可见性**：地形 PSO 创建返回 `E_INVALIDARG`，调试层原文 `Root Signature doesn't match Pixel Shader: Shader CBV descriptor range (BaseShaderRegister=0 …) is not fully bound in root signature` —— HLSL 在全局声明了 `cbuffer`（VS/PS 都登记了 b0），但根参数只给了 `D3D12_SHADER_VISIBILITY_VERTEX` ⇒ 必须给 `ALL`（或把 cbuffer 只声明在真正需要的阶段）。
- **坑 4｜缓冲区资源描述**：`CreateCommittedResource` 建 buffer 时 `Height`/`DepthOrArraySize` 不能留 0，调试层原文 `D3D12_RESOURCE_DESC::Width, Height, and DepthOrArraySize cannot be 0. The minimum value is 1` ⇒ 必须 `Height = 1、DepthOrArraySize = 1、MipLevels = 1`。
- **附带两条**：①dx 层错误路径原先用 `Log::printError` ⇒ 该函数 `while(true)` 挂死（进程不退出、截图拿不到），dx 侧 22 处已全换 `Log::printWarning`；②窗口化 flip 呈现的**前 1~2 秒**会被节流到刷新率（~120 fps），**稳态**才反映真实性能（本例稳态 ~440 fps / 2.3 ms），据此判断瓶颈时务必看稳态样本。
## 全屏性能：黑屏根因与两种全屏的差异（2026-10-01）
- **黑屏根因（已修）**：调用 `IDXGISwapChain::SetFullscreenState(TRUE)` 切到独占全屏后，**必须按新模式 `ResizeBuffers` 并重建 RTV**，否则 DXGI 呈现不出内容（纯黑）——症状很迷惑：帧率正常、无报错，但画面全黑。修法：`DxSwapchainNode::resize()`（释放旧视图 → `ResizeBuffers` → 重建 RTV 堆与视图），切换后立即调用；随后用 `GetDesc().BufferDesc` 取**实际后备缓冲尺寸**，作为深度缓冲、视口、相机纵横比的唯一来源（独占全屏可能匹配到就近模式）。
- **两种全屏差异（同分辨率 2560x1440、同内容、都 vsync 关）**：

  | 配置 | 稳态 | 帧时 | 说明 |

- **症状**：`fe-dsh` 第一次启动总报「✗ 8 秒内 3080 未监听」，紧接着第二次就成功 —— 看着像随机故障。

- **配套的关闭侧漏洞**：`fe-dsh-end.ps1` 只按 3080 端口占用者反查进程链 ⇒ 对「还在启动、尚未绑端口」的子进程看不见，会报「无需关闭」后它稍后自己绑上端口（「以为关了」）。正解：启动方落 PID 文件（`build\temp\work\dsh.pid`），关闭方按 **端口占用者 ∪ PID 文件** 双来源定位，并用 `taskkill /PID x /T /F` 连子进程树一起清、末尾删 PID 文件。另实测：正常启动 ≈28~35 秒 ⇒ 超时阈值给 120 s，且**超时不杀**（贸然杀会打断刚要做完的引导）。
- **验证手法**：`[System.Management.Automation.Language.Parser]::ParseFile` 做语法解析 + 脚本自带 `-DryRun`（在启动前 `exit 0`，不碰端口）⇒ 改完不必真启动就能自检。

## 枚举空值：`none` 是语义值、`enumNull` 是哨兵，两者不可互换（2026-10-02 定稿）
- **`none`**（放**首位**、值 0）：表示「不启用/不偏移/不测试/不写颜色/无」这类**语义值**，本身就是默认值。例：`biasId::none`、`stencilId::none`、`writeMaskId::none`、`dynamicId::none`、`lodSourceId::none`。
- **`enumNull`**（放 **`enumCount` 之后**、取值 n+1、**无尾逗号**、落在计数范围外）：表示「**未指定**」哨兵。判据是**原代码里出现的 `= X::enumCount`** —— 拿越界的长度值硬凑空值（实测有 `renderAttId` / `renderTemplateId` / `descType` / `cubeId` / `terrainLayer`）。
- **踩过的坑**：我一度把上述 5 个 `none` 统一改名成 `enumNull`，用户指出会产生歧义（让人误以为是空指针式的未指定）⇒ 已全部还原为 `none`（定义 + 9 处引用）。**别再用 `null` 去替代 `none`，反之亦然**。
- **判别优先级**（本轮实测）：**哨兵用法 `= X::enumCount`** > 默认赋值 `= X::<真实成员>`。只看「默认赋值」会被**数据赋值**骗到（`cubeId` 被算出 49 处假默认 ✗），只看注释会被「注释里写着默认」骗到。

## 采样器与管线解耦：maxLod 不要绑运行期 mip（2026-10-02）
- **原状（互锁）**：采样器 maxLod 取自 `pipeTerrain.texture.mipLevel` 与 `pipeModel.getMaxModelMip()` ⇒ 采样器依赖管线 create 的产物；而未来的描述符又要用采样器表 ⇒ 成环，导致「描述符全归管线」无法实现。
- **解耦**：`samplerEnum::lodSourceId` 两态改为 `none`（maxLod = 0）／`clampNone`（maxLod = `VK_LOD_CLAMP_NONE`）—— 采样 LOD 先被 [minLod,maxLod] 夹、再由纹理自身 mip 层数夹 ⇒ 「不限制」等价于「全用上」，无需知道真实 mip 数。

- **通则**：能让硬件兜底的语义就不要绑到运行期数据上 —— 绑定会把本可独立的创建顺序变成串行甚至成环。
## descriptor buffer 切换 · 经验（2026-10-05）

### 一、必备条件
- VMA 开 `VMA_ALLOCATOR_CREATE_BUFFER_DEVICE_ADDRESS_BIT` ＋ `vulkanApiVersion >= 1.2`（否则 vmaCreateBuffer 报 -3）。
- UBO 缓冲带 `VK_BUFFER_USAGE_SHADER_DEVICE_ADDRESS_BIT`（否则 02601）。
- 管线 `VK_PIPELINE_CREATE_DESCRIPTOR_BUFFER_BIT_EXT`（否则 08117/08600）。
- 布局 `VK_DESCRIPTOR_SET_LAYOUT_CREATE_DESCRIPTOR_BUFFER_BIT_EXT`；用法位是 `VK_BUFFER_USAGE_RESOURCE_DESCRIPTOR_BUFFER_BIT_EXT`。
- `vkCmdBindDescriptorBuffersEXT` / `vkCmdSetDescriptorBufferOffsetsEXT` loader 不导出 ⇒ 必须 vkGetDeviceProcAddr。

### 二、写表与读取必须同源编号（最贵的一课）
- 现象：模型贴图/大小错、地形出现"缩小的一份"、GPU 干跑到卡死。
- 根因：写入用"家族游标自增"、读取用"公式算下标" ⇒ 串号。
- 正解：`writeFrom(device, tNodeIndex, requests)` 显式下标，两侧同一公式；共用家族必须分区（terrain=0，model 从 1 起）＋ 容量常量注明占位。

### 三、上传时机（DEVICE_LOCAL 描述符缓冲）
- 首选：把 `vkCmdCopyBuffer` 录进本帧命令缓冲（第一个 render pass 之前）并加 TRANSFER→SHADER_READ 屏障 ⇒ 无需额外 pool/cmd/fence 与 vkQueueSubmit。
- 独立通道的两种坑：过早 ⇒ vkQueueSubmit 返回 -4 DEVICE_LOST；过晚（帧末）⇒ 第 1 帧空描述符。

### 四、收尾
- 每节点两块缓冲纳入 clear（否则 vkDestroyDevice 报一串 05137）；独立通道的 pool/cmd/fence 必须销毁。

### 五、清池残留（零风险方法）
- 用符号计数死活判定：`vkUpdateDescriptorSets` / `VkDescriptorPool` / `createPool` / `setAllocInfo` / `VkWriteDescriptorSet` 为 0 即死代码。
- 只删描述符池标识，别误删命令池（VkCommandPool 合法）。
- 删字段前先 grep 读取点（本次 `VkWriteDescriptorSet write{}` 看似孤立，其实构造体内 5 行赋值在用 ⇒ 须同批删）。

- **坑 1：先插入后删除** ⇒ 新插入的字段/行会被同一条删除正则误删（本次 descLayoutNode 的 3 个字段就这样被删掉，报"不是成员"）。正解：**先删旧、再插新**。

### 三、教训：同类型既当"模板"又当"实例"是隐患
- 现象：`descNode` 里 `descBuffer`（家族模板）与 `descBufferList[i]`（每节点）是**同一个类型**，字段整份复制 ⇒ 存在"副本必须永远同步"的隐性契约。

- 结论：凡是"定义/模板"与"实例"共用一型，且实例是 N 份 ⇒ 尽早拆型；与"写读同源编号"是同一类治理。
### 四、类型内嵌（nest）后的必然连带：脱前缀（2026-10-05）
