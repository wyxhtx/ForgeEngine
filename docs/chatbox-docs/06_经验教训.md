> 用途：踩坑先查；AI 修复任务会自动向本文档追加新条目（自动沉淀机制，见文末）。

## 编码类

- **现象**：.ps1 中文乱码 / bat 中文乱码
  **规则**：.ps1 = UTF-8 带 BOM；代码/.md = UTF-8 无 BOM；bat/txt = ANSI(GBK)
- **现象**：VS 输出窗 vcpkg 中文乱码（濮濓絽婀...）
  **根因**：vcpkg 输出 UTF-8，VS 按系统 GBK 解码
  **解决**：无（显示层问题）；命令行看正常
  **防御**：构建正常即可忽略，排查用命令行
- **现象**：VS 输出窗口里**自己写的**构建期工具（ForgeReflect）中文日志乱码成"鍙嶅皠鐢熸垚"，同一份日志里 CMake 写的 `反射生成：DescriptorConfig.gen.h` 却正常（注：该构建期工具 2026-09 已删，反射改运行期现算；转码这条经验对任何自研构建期工具仍适用）
  **根因**：工具用 std::cout 吐 UTF-8，而 VS/MSBuild 捕获子进程 stdout 时按**本地代码页**解码（.NET Framework 的 `Encoding.Default` = ACP = 936）；CMake 的 COMMENT 不走子进程 stdout（它是工程文件文本），所以两种中文命运不同
  **解决**：工具输出前转码：UTF-8 → 宽字符 → 目标代码页；目标页取 `GetConsoleOutputCP()`，为 0（无控制台 = VS/MSBuild 的 CreateNoWindow 管道）时取 `GetACP()`。实测无控制台路径吐 GBK 字节 `B7 B4 C9 E4 C9 FA B3 C9 A3 BA`（按 936 解码即"反射生成："），有控制台路径跟随控制台代码页（chcp 65001 时仍是 UTF-8）
  **防御**：①自研构建期工具凡输出中文都要走这个转码（`toOutputCode`），**别指望 `SetConsoleOutputCP`**——无控制台时它不生效，改了也白改 ②验证编码问题必须看**原始字节**（`ReadAllBytes` + 按目标代码页 `GetString`），用默认 UTF-8 读文件会得出错误结论（本次就先用旧 exe 验了一轮才排除）③第三方工具（vcpkg）的同类乱码只能忽略

## PowerShell / 执行类

- **现象**：PS7 里 [System.IO.File]::ReadAllText 相对路径去 system32 找
  **根因**：PS location 与 .NET CurrentDirectory 不同步
  **防御**：脚本内一律 Join-Path $PWD（绝对路径）
- **现象**：粘贴多行命令报 Get-Process / else 报错
  **根因**：复制内容混入历史提示符；交互式 if/else 分行
  **防御**：只复制代码块本体；if/else 写单行；整块一次粘贴勿逐行敲；命令块开头加 cls 清屏（07 协议）
- **现象**：占位符 <...> 被原样执行，覆盖文件
  **防御**：执行前确认无 < 占位符未替换
- **现象**：here-string 直接放方法参数 → ParserError
  **防御**：先存变量（$x = @'...'@）再传参
- **现象**：字符串 Replace 不命中（静默）
  **根因**：替换串空格数/全半角与原文不符
  **防御**：先 Select-String 原文核对再 Replace；先长后短

- **现象**：`$raw -replace [regex]::Escape('a' + $x + 'b'), 'c' + $y` → 报 "The -replace operator allows only two elements to follow it, not 4"
  **根因**：`-replace` 的右侧操作数按**参数模式**解析，空格分隔的表达式会被拆成多个数组元素（4 个）
  **解决/防御**：字面替换一律用 `$s.Replace($old, $new)`，且先把 `$old = '"' + $x + '"'` 算好再传；确需正则才用 `-replace`，两侧各先存变量

- **现象**：行级替换切坏 .ps1——用"行号定位起止+数组重组"替换 forgeEngineCmdList.ps1 的函数段，定位错位切掉文件大段，dot-source 报 ParserError（Unexpected token '}'）
  **根因**：函数结尾用"行首恰为 }"判定，文件内其他行首 } 干扰匹配；函数实际在文件末尾，行号假设错误
  **解决**：git checkout -- 文件恢复 HEAD 底稿 → 纯追加（ReadAllText + 末尾拼接 + WriteAllText 保 BOM/CRLF）重建
  **防御**：①向现有 .ps1 加函数一律"末尾纯追加"，禁止行级替换/数组重组 ②动手前 git ls-files 确认有底稿可回滚 ③验证文件干净先 Remove-Item function:xxx 清内存残留再 dot-source（否则旧函数仍在会话，Get-Command 误判未改干净）④加分区注释前先 Select-String '^# [一二三四五六七八九十]+、' 查已有编号（本次误写"三、"实为"七、"，撞"三、查看"）
- **现象**：手写解决方案 `build\ForgeEngine.slnx` 被"按关键词删行"的脚本改坏（留下孤立的 `<BuildDependency>` 与多余的第二个 `</Project>`）→ VS 打不开；同一轮里 `cmd\forgeEngineCmdList.ps1` 被无 BOM 编码写回，**BOM 丢失**
  **根因**：①按行过滤 XML 会拆散标签配对，而我只按"行数对不对"验收（20→15 就以为成功）②批量改写统一用了 `UTF8Encoding($false)`，没区分 `.ps1` 必须带 BOM
  **解决**：`build\ForgeEngine.slnx` 从 HEAD 还原（13 行，`[xml]` 解析通过、与 HEAD 逐行 0 差异、MSBuild 构建 exit 0）；`.ps1` 用 `UTF8Encoding($true)` 写回后自检 BOM/CRLF，并与 HEAD 逐行比对确认"只多了一行"
  **防御**：①改 XML / `.slnx` / `.vcxproj` 后**必须 `[xml](Get-Content -Raw)` 解析校验**，不能只看行数 ②凡改 `.ps1` 一律带 BOM 写回并自检 ③一切批量改动的验收 = **回读内容/结构**（逐行比对或解析），行数只作辅证 ④改工作区外文件（如库）前先看它的 EOL/BOM 约定，别套用别的目录的
- **现象**：脚本批量重排大文件（54 个结构体 / 3300+ 行）时把文件改坏（静默多插 759 行），另一版脚本静默丢内容
  **根因**：①`@(@('clear',3))` 这种"单元素嵌套数组"被 PowerShell 展平成 `@('clear',3)`，取 `$pair[0]`/`$pair[1]` 得到字符 'c'/'l'，模式变量变 `$null`，而 `-match $null` 匹配任意行 ⇒ 改到错误位置 ②函数块收集只看签名行、不配平括号/花括号（多行签名、`template<>`、单行体 `{ … }`、注释里的括号都会误判）⇒ 函数体被当"无法归类"或被丢弃 ③调整完"前置空行"后仍用**过期行号**去数"后置空行"，吃掉刚插入的行
  **解决**：内容先 `Copy-Item` 备份到 build\ 下；坏掉后用**只读** `git show :<path>` 从索引恢复（恢复后与索引逐字节一致）；脚本内置"每个单元非空行**内容多重集**不变"校验，任一单元不符就跳过不动它
  **防御**：①批量改结构/格式的脚本一律"默认干跑、`-Apply` 才落盘"，并打印逐单元变更清单 ②校验用**内容多重集**（非空行排序后取哈希）而不是行数——它同时抓得住丢失与重复 ③验收补一条**幂等性**：改完再干跑一次应报"0 变更"，否则说明规则没落全 ④别用 `@( @(a,b) )` 传多字段参数，改用具名字段（hashtable）或多条独立语句 ⑤内联 pwsh 命令里避免嵌套引号（`"$($x.Contains('y'))"` 会解析失败、整段不执行且无输出），先赋值给变量再拼接 ⑥别用 `| Select-Object -First N` 截断"会写盘"的脚本输出——`-First` 取够对象就**终止上游管道**，而写盘在脚本末尾 ⇒ 文件根本没写、脚本被半路掐断（本次 `-Apply` 就这样白跑一次，靠 mtime 未变才发现）；要截断先把输出存进变量再取 ⑦PowerShell 变量名**大小写不敏感**：`$D`（备份根路径）与 `$d`（循环变量）是同一个变量，本次曾因此把路径覆盖成 `03-种族`、还在工作区建出 3 个垃圾目录——路径类变量一律用多字符名（`$Root`/`$Dest`）

## CMake / 构建类

- **现象**：CMakePresets.json 加 // 注释 → JSON Parse Error
  **根因**：preset 解析不接受注释（实测）
  **防御**：preset 保持严格 JSON；说明写文档
- **现象**：目录改名后 cmake 报 CMakeCache 路径不匹配
  **根因**：cache 固化旧绝对路径
  **解决**：fe-clean（删 build\vs，保留 vcpkg_installed）→ 重配
- **现象**：ForgeEngine.dir / x64 / Debug 等空目录与中间目录
  **根因**：VS 生成器硬编码（IntDir 不可配）
  **防御**：接受；exe 已收 bin\output
- **现象**：VS 出现 "CMake Rules" 节点
  **根因**：自定义规则输出文件（spv）进了 target_sources
  **解决**：assets GLOB 排除 shader\（规则产物）
- **现象**：exe 输出目录写死绝对路径
  **根因**：CMAKE_BINARY_DIR 展开（CMake 设计）
  **防御**：别手动改 vcxproj，改 CMakeLists 的 RUNTIME_OUTPUT_DIRECTORY
- **现象**：想自定义 "Fast" 配置档 → vcpkg 失败
  **根因**：vcpkg 只认内置配置名（非标准配置转储/链接错库）
  **防御**：不自定义新配置名；用内置 RelWithDebInfo 重定义 flags（现配置集 Debug;Release;RelWithDebInfo，RelWithDebInfo=/DNDEBUG /Od /Zi 快速日常档，带 PDB 可断点）
- **现象**：单 TU Release /O2 全量 ~12.4s（/d1reportTime：前端 ~2.8s、后端 ~9.6s）；/cgthreads8 无效
  **决策**：日常用 RelWithDebInfo（~6s）；Release 仅发布/优化验证跑 → 现阶段不拆 TU
  **根因**：全 inline 头设计 → codegen 锚定调用点（main→Pipeline::drawFrame/ctor→Plate/Buffer/3 worker 全链）；"世界/初始化/帧/工具"4 路均分需所有权解耦（Plate 移出 Pipeline）+ namespace 全局 inline 化（VkInfo.h engineInfo/lockInfo/getLock 等 LNK2005 风险），现实上限 ~6-7s
  **防御**：复评触发 = 全量 >20s 或频繁改头文件痛感明显；届时先做 Pipeline 方法定义下沉 graphic\Pipeline.cpp（声明留类内）→ 再做 Plate 解耦；任何多 TU 前先 C0：namespace 级非 inline 全局改 inline
- **现象**：想让 VS 的中间目录跟手写工程一样落到 bin\intermediate\x64\<Config>（obj / pch / pdb / tlog / recipe 一并），但 CMake 生成的 vcxproj 里 <IntDir> 写死为 <Target>.dir\<Config>
  **根因**：CMake 的 VS 生成器没有 IntDir 配置项；VS_GLOBAL_IntDir 写在 Globals 属性组（先于逐配置属性组）会被覆盖。另有两处不吃 $(IntDir)：① DesktopDeployRecipeFile 由 Microsoft.CppBuild.targets:37 在**评估期**用当时的 IntDir 定死默认值 ② CMake 给 cmake_pch.cxx 写的 PrecompiledHeaderOutputFile 是**绝对路径**，元数据评估期固化
  **解决**：config\cmake\ForgeIntermediate.targets（源）+ CMakeLists 的 configure_file(... ${CMAKE_BINARY_DIR}/Directory.Build.targets COPYONLY)。该文件由 MSBuild 在工程**末尾**导入：PropertyGroup 里重赋 IntDir 与 DesktopDeployRecipeFile；再用 <Target BeforeTargets="ClCompile"> 内不带 Include 的 <ClCompile>（= 改全部现有项）改写 PrecompiledHeaderOutputFile 元数据。实测 Main.obj / cmake_pch.pch / vc145.pdb / recipe / tlog 全部落到 build\vs\bin\intermediate\x64\Release\，build exit=0
  **防御**：①只覆盖主目标（Condition="'$(MSBuildProjectName)'=='ForgeEngine'"）——多工程共用同一 IntDir 会触发 MSB8028 ②Directory.Build.targets 属 MSBuild 侧覆盖，CMake 不知道（vcxproj 里 IntDir 原样），别去手改生成的 vcxproj ③ForgeEngine.dir\ 等空壳目录会被生成器每次 configure 重建（0 文件），无法消除 ④用 configure_file（不是 file(COPY)）源变更才会自动重配 ⑤改完必须重新 configure + 实编，不能只看 vcxproj 文本 ⑥同类残留要一次查完：辅助工程的默认 IntDir `$(Platform)\$(Configuration)\$(ProjectName)` 与默认 OutDir `$(SolutionDir)$(Platform)\$(Configuration)\` 会留下 `build\vs\x64\`；ForgeEngine 的 `<ImportLibrary>…\build\vs\<Config>\ForgeEngine.lib`（EXE 用不到 import lib）会被 `Microsoft.CppBuild.targets:1450` 按 `%(Link.ImportLibrary)` 建目录，留下空的 `Release\` / `RelWithDebInfo\` —— 两者都在同一 targets 文件里改指 `bin\intermediate` 即可（辅助工程各自子目录，避免 MSB8028），改完只剩生成器创建的 `<target>.dir\` 空壳

- **现象**：构建期生成的源文件（如反射生成的 `DescriptorConfig.gen.h`）改了内容，引擎却不重编；用 `| Select-Object -First N` 过滤构建输出后，下次构建报 MSB6003 `文件"…\CMAKE_PCH.PCH"正由另一进程使用`（注：该生成头 2026-09 已取消，教训对"任何构建期生成物"仍适用）
  **根因**：①生成头是"编译输出"而非"手工源"，MSBuild 靠 `TrackFileAccess` 的 tlog 才知道它是 `Main.cpp` 的依赖；`-p:TrackFileAccess=false`（本会话为绕沙箱固定加的参数）会关掉这层跟踪 ⇒ 生成头变新不触发重编 ②`Select-Object -First N` 取够 N 条对象就**终止上游管道**（同 L42⑥），构建被半路掐断、留下孤儿 `CL.exe` 占着 PCH，下一次构建才以 MSB6003 暴露
  **解决**：验证生成物改动时强制重编（改一次 `Main.cpp` 或 fe-clean 该目标）；构建命令一律 `cmd /c "… > build\temp\log\x.txt 2>&1"` 全量落盘，再对日志文件 `Select-String`
  **防御**：看到 MSB6003 "文件正由另一进程使用"先查残留 `CL.exe`（`Get-Process cl,link,MSBuild`，按启动时间认陈旧进程）再重试，别怀疑源码；凡"生成物 → 编译"的依赖链，验证时都要显式确认产物时间戳真的变了

## vcpkg 类

- **现象**：cmake --preset vs 突然全量重建 22 包
  **根因**：triplet/portfile/baseline 内容变 → ABI 变
  **防御**：triplet 改动要预期一次性重装（跑完即稳）；勿随意加空格改内容
- **现象**：改 triplet 注释也触发重建？（待验证——若 vcpkg 按文件 hash 计 ABI，注释也变）
  **防御**：triplet 尽量少动；动前知晓会重建
- **现象**：vcpkg.json 删依赖行后，已装包仍留在 vcpkg_installed？
  **解决**：删行 → cmake --preset vs → manifest 自动卸载（实测删除 forgeengine-stb-font："Removing 1/1...8.49ms"，无需手动删目录）
  **防御**：删库=vcpkg.json 删一行 + reconfigure；以 vcpkg 输出"will be removed"为准，残留无害
- **现象（2026-09 已正式迁移，此条为结论）**：VS2026 与 VS2022 混用会导致 exe/库混链，链接报 ktx LNK2019 __std_unique_4
  **根因**：vcpkg 无视 vcvars/VCToolsInstallDir，固定 `vswhere -latest` 选最新 VS；只要 exe 与依赖库的工具集不同 → STL 内部符号不匹配
  **迁移做法（路线 B：整条链迁 VS2026）**：① `CMakePresets.json` 生成器 `Visual Studio 17 2022` → `Visual Studio 18 2026`（需 CMake ≥4.2；实际用 VS2026 自带的 4.3.1，把其 bin 前置到 User PATH）② 删 `VCPKG_VISUAL_STUDIO_PATH`、`VCPKG_PLATFORM_TOOLSET=v145` ③ 删 `build\vs` + `build\vcpkg_installed` ④ `cmake --preset vs`（全量重建 29 包，实测 6.5 分钟）→ `fe-br`
  **验证**：`CMakeCache.txt` 的 `CMAKE_GENERATOR:INTERNAL=Visual Studio 18 2026`；各 vcxproj `<PlatformToolset>v145</PlatformToolset>`；cl 为 14.51；构建/运行无 LNK2038、无 LNK2019
  **回滚**：`VCPKG_VISUAL_STUDIO_PATH=<VS2022路径>` + `VCPKG_PLATFORM_TOOLSET=v143` + 生成器改回 `Visual Studio 17 2022` + 删 `build\vcpkg_installed` 重建（binary cache 秒回）
  **防御**：改工具链必须"生成器 / 工具集 / 环境变量 / 依赖"四处同时改；VS2022 不卸作兜底；两个 VCPKG_* 变量写 User 级后需广播或重开终端

- **现象**：日志停在 `Fetching registry information from https://github.com/microsoft/vcpkg (HEAD)...`，像注册表抓取卡死（且系统内无 git.exe 进程）
  **根因（实测纠正）**：抓取没卡——libgit2 **确实套用**全局 `url.insteadOf`。证据：`%LOCALAPPDATA%\vcpkg\registries\git\.git\FETCH_HEAD` 写的是 `https://ghfast.top/https://github.com/microsoft/vcpkg`，且**无 `.git` 后缀** ⇒ 用的是 vcpkg 内置 URL 串、不是 origin。真凶是 vcpkg 的**工具获取**：PortableGit / cmake 走普通 HTTPS、不经过 git，`insteadOf` 管不着 → 直连 github 大文件挂死。"无 git.exe 进程"只证明走 libgit2，**不能反证 insteadOf 无效**
  **解决**：用镜像把工具包按 vcpkg 要的**原文件名**预置到 `$env:VCPKG_ROOT\downloads\`（本次：`PortableGit-2.55.0.3-64-bit.7z.exe` 58,919,776 B、`cmake-4.4.0-windows-x86_64.zip` 54,388,920 B）→ 日志变 `Extracting cmake...`（无 Downloading 行）
  **防御**：判卡点看"有没有 `Downloading` 行"；改 origin 无用（内置 URL 不读 origin）；别把"insteadOf 无效"当成结论
- **现象**：工具版本被动抬升（cmake 3.31.10→4.4.0、git 2.53.0→2.55.0.3）后 29 包全量重建、`Restored 0 package(s)`
  **根因**：`vcpkg_abi_info.txt` 记的 `cmake <版本>` 与编译器哈希都参与 ABI。删 `%LOCALAPPDATA%\vcpkg\registries` 后重新拉取的镜像 HEAD 是 2026-07-27（本地 baseline `61d43ee` 的 pin 为 2026-03-04）→ 工具元数据失配 → 回退内置新版本 → ABI 全变
  **实测**：`cmake --preset vs` 全量重建 29 包 6.7 分钟（与 02 记录的 6.5 分钟一致），属一次性
  **防御**：①工具版本/注册表缓存变更 = 预期一次性全量重建，别为省它回退工具链 ②诊断用 `vcpkg install --dry-run --debug`（只算不建，可读每包 ABI 与编译器哈希）③`VCPKG_PLATFORM_TOOLSET=v143` 单独改**无效**——编译器哈希由 `vswhere` 选中的 VS 实例决定（实测 VS2026/14.51=`f61d16a2`、VS2022/14.44=`fa58befc`、13:20 缓存=`7657bc53`，三者互不相同），换实例须 `VCPKG_VISUAL_STUDIO_PATH`
- **现象**：VS 生成报 MSB3073 退出码 3，输出"系统找不到指定的路径。"（编译/链接均成功，仅 ForgeEngine 的 post-build 失败）

- **试点结论**：dsh（DeepSeek Harness 0.1.2-rc）作为 ForgeEngine 执行体试点判定：方案 C（Chatbox 大脑 + dsh 执行体）成立
  **实测事实**：pwsh 持久会话；fe- 指令跨会话可用（免 dot-source）；只读命令零审批；中文读写无乱码（后续 2026-09-23：Chatbox 弃用，改 dsh 单轨，见 08_工作流.md）

- **现象**：DSH 会话里 `cmake --preset vs` 或触发 ZERO_CHECK 重新生成时配置失败——`-- Running vcpkg install` → `write_contents_and_dirs("E:\tool\app\vcpkg\buildtrees\0.vcpkg_dep_info.cmake"): permission denied` → `CMake Error at vcpkg.cmake:953 (message): vcpkg install failed` → MSB8066；同一命令在 VS / 普通终端正常
  **根因**：DSH 文件沙箱（workspace-write）只允许写会话工作区，而 vcpkg 必须写工作区外的 `$VCPKG_ROOT\buildtrees`；报错由 vcpkg 自己打印，没有 harness 的 `[sandbox: file access denied]` 标记，易误判为 CMakeLists 语法错
  **解决**：配置/重新生成在 VS 或普通终端执行；确需在 DSH 里跑就对该命令一次性放宽到 danger-full-access（需审批；每次 configure 都要，因为 vcpkg 每次都写 buildtrees）
  **防御**：看到 `vcpkg.cmake:953` + `permission denied` 先看被拒路径是否在工作区外，先排除沙箱再查脚本；DSH 内做纯编译验证走 `cmake --build build\vs --config Release --target ForgeEngine -- /p:TrackFileAccess=false`（generate.stamp 最新时不触发 vcpkg，workspace-write 即可完成；该开关用于绕过沙箱对 MSBuild 文件跟踪器的拦截）

- **现象**：DSH 沙箱（workspace-write）下用 MSBuild 构建，报 `error TRK0002: ... CL.exe ...` → `MSB6006: "CL.exe" 已退出，代码为 2`
  **根因**：MSBuild 的文件跟踪器（`TrackFileAccess` 默认 true）通过命名管道与 `CL.exe` 通信，沙箱禁止命名管道 ⇒ 跟踪器拉起 `CL.exe` 的阶段即失败；该失败**早于编译**、与源码 / CMake 无关（改代码无用）
  **解决**：构建命令一律带 `-p:TrackFileAccess=false`（实测加该参数后 0 错误 0 警告）
  **防御**：见 `TRK0002` + `MSB6006`（CL.exe 退出码 2）先怀疑沙箱文件跟踪，别查源码；DSH 内构建固定用 `cmake --build build\vs --config Release --target ForgeEngine -- /p:TrackFileAccess=false`

【编辑器工具改脚本】用 `$t.Replace(锚点, 补丁 + 锚点)` 做"插入"会**全量替换**所有同名锚点——本会话因此把重排脚本复制成 5 份，且重复块被塞进 `@{Expression = { param(...) ... }}` 排序键脚本块里（`param()` 恰好合法，`Parser::ParseFile` 报 0 错、静默通过），结果排序键每比较一次就跑一遍整棵树 → 单文件干跑从 1 秒变 124 秒+。
防御：①插入/替换只改**第一处**（用 `IndexOf` 断言唯一后拼接，或 `[regex]::Replace(..., 1)`）②改完查**行数是否异常膨胀** ③断言"关键字出现次数 = 1"④`Parser::ParseFile` 语法自检**不足以**发现整份重复，必须配合行数/次数检查。⑤编辑 `.ps1` 后复查 BOM 是否被工具剥掉。
【规则改动先量化影响面】给排版脚本加新规则时，先在 `build\` 复制一份**原型脚本**（改原型、不动正式件），用**全树干跑**列出"被改文件清单"再决定是否收窄。本次"同后缀家族"（`mouseHandle`/`keyHandle`/`scrollHandle` 并组）原型一次就暴露两处非预期重排：`Buffer.hpp`（族并层把 L2 的 createVertexBuffer/IndexBuffer 拉到 L1，层边界下移）、`Plate.hpp`（谓词 `isHandleChangeCubeList` 与 `handleChangeCubeList` 被当兄弟上拉）。
防御：①新规则先在原型里跑全树干跑，只打印 `重排=True` 的文件清单 ②每个非目标文件都要能解释"为什么变"，解释不了就收窄规则 ③收窄用**可命名的排除项**（本次：派生名 / 族内已知层不唯一 / 族内互相调用），不要硬编码文件名或跳过清单 ④正式件只落"全树影响面 = 仅目标文件"的版本。

【大小写】判断"派生名"用 `$a.EndsWith($b)` 会**区分大小写**：`isHandleChangeCubeList` 的末 20 字符是 `HandleChangeCubeList`（大写 H），与 `handleChangeCubeList` 不相等 ⇒ 判断失效、规则照常生效（Plate.hpp 被误改，靠全树干跑才发现）。正确写法：`$a.ToLowerInvariant().EndsWith($b.ToLowerInvariant())`。
防御：凡"包含 / 前缀 / 后缀"类名字判断，先明确是否要区分大小写；本项目函数名大小写**有意义**（`is` 前缀、`Init` 前缀），但**同族/派生判定必须忽略大小写**；判断失败时先用两行独立复现验证（`'A'.EndsWith('a')`）再改脚本。
