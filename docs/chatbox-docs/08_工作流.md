## 协作协议要点

- **影响卡先行**：改动前给"方案影响卡"（文件 / 逻辑 / 风险 / 回滚）→ 等用户确认。
- **命令块三段式（改 → 验 → 提交）**：多文件/命令改动 = ①改 ②验证带预期 ③提交；单文件改动 = 给完整文件。
- **命令块开头一律 `cls`**：清屏，防历史输出/提示符混入误判；破坏性命令附回滚。
- **验证贴回核对**：用户执行后贴输出，dsh 判读推进；输出精简，只贴验证结果/报错行。
- **提交纪律**：每逻辑单元一次 commit；勿逐小步急交；git 永远用户手动。
- **T 模板**：T1 方案讨论 / T2 解释 / T3 单文件 / T4 多文件命令块 / T5 诊断 / T6 审查（分级清单）。
- **任务卡**：【类型】【对象】【约束】。
- **沉淀**：修复类收尾把可复用教训追加到 `06_经验教训.md`（查重后），与 commit 同批。

## 铁律（与 `AGENTS.md` 同步）

1. 绝不执行 git 写操作（commit / push / add 全禁）

6. 破坏性动作（清理 / 删除 / 覆盖）等用户发话
7. 规范 / 约定变更按预授权同步进 Obsidian 库

## 图表 / 流程图产出规范（2026-09-26 定）

画流程图**默认用 Obsidian 画板（`.canvas`）**，不要手写 HTML 示意图充数：

- **落点**：库根 `铸造\<主题>流程图.canvas`（总览 / 讨论用大图 ✓）；**仓库 `docs\` 不放画板** ✗（GitHub / VS 不渲染 `.canvas` ✓）。
- **先数据后渲染**：先产出「节点表 + 边表」（纯文本 ✓ 每节点带 `文件:行号` 与产出物 ✓），确认后再渲染成 `.canvas` JSON（v1.0：`{"nodes":[…],"edges":[…]}`）✓。
- **节点三行**：`步骤名` / `文件:行号` / `产出物`（每行 ≤30 字 ✓）；**一图一义** —— 主干、分支、构建顺序链分开画 ✓。
- **阶段分组**：用 `type:"group"` 分组（四阶段各一色 ✓），分支支线贴在主干对应节点旁 ✓。
- **行号不许写死** ✗：生成脚本按「代码文本 / 符号名搜索」定位行号 ✓，否则改一次代码图上的行号全漂 ✗。
- **自检三项（必须脚本实测出数字，不能自称"已检查"）**：① JSON 可解析 ✓ ② 每条边的端点都存在 ✓ ③ 矩形零重叠且所有非组节点都被组包住 ✓。
- **编码**：`.canvas` = UTF-8 无 BOM / **LF** / 末尾无换行 ✓（库约定）；生成脚本 `.ps1` 带 BOM ✓。
- **旁证格式**：需要"能随代码 diff 的准图"→ 同一份节点/边表另出一份 **Mermaid** 代码块 ✓；需要网页验收 / 展示 → 自包含 **HTML + 内联 SVG** ✓（无外链 ✓）。
