# 09 管线预设（九类：七大类 + 两个正交小类）

引擎的管线配置拆成**九类枚举**（89 项），每类走「**enum 类型 → 配置结点只写差异 → 成品装配结点私有 `createXxx` 译入**」三步：**枚举是类型、配置结点是差异、装配结点里译入只此一处**。⚠ **2026-09-28 改制**：原先的「预设结点 `xxxNode` → 预设表 `xxxList` → `resolvePipePreset()` → `pipeStateNode`」四步**已删除**；本文件下方的枚举项清单与管线取值表仍然有效，但**代码位置**请按本节新结构读。

- 上级：[[01_总览]]　相关：[[02_构建体系]]、[[03_源码模块]]
- 代码位置：枚举 `data\VkEnum.h`；配置结点 `pipeConfigParamNode` + 成品装配结点 `pipeConfigNode`（含私有 `createPrimitive` / `createRaster` / …）+ 9 个每管线结点 `pipeXxxNode` 都在 `data\VkStruct.h`；9 处显式 `node[管线].createPipelineNode(...)` 在 `data\VkList.h` 的 `procPipelineNode` 构造里（元数据 + 装配都在 `VkStruct.h` 的 `pipelineNode`）；运行期实参由 `graphic\Pipeline.hpp` 在成员初始化处一次注入（`procPipeline{ Device.device, 描述符结点.node, renderList, msaa }`），构造体内建家族布局 ×5 与管线缓存（**无 `isLayoutBuilt`**）；建 VkPipeline 走 `buildPipeline(id, extent)`
- 表规模：11 + 23 + 18 + 12 + 7 + 7 + 3 + 4 + 4 = **89 项**（枚举项数；**枚举顺序 = 审计里的预设序号**）

## 一、三层结构

```
VkEnum.h     primitiveId::type / rasterId::type / … / logicOpId::type        九类枚举（类型即参数）
                 ↓ 调用行只写差异：pipeConfigParamNode{ .depthType = depthId::… }
VkStruct.h   pipeConfigParamNode                                            配置结点（九个枚举字段 + = 默认值）
                 ↓ createPipeConfigNode(param, 运行期实参…)
VkStruct.h   pipeConfigNode::createPrimitive / createRaster / createDepth /… 私有译入（各一个 switch，类型→值只此一处）
                 ↓ 成品落 Vk 结构体 + 运行时喂入（着色阶段 / 顶点输入 / 视口裁剪 / 采样数）
VkStruct.h   pipeConfigNode（成品） + pipeXxxNode ×9                        每管线结点（descriptor 集合 / mesh）
```

1. **枚举**：一类一个 `namespace xxxId { enum type { … count } }`，纯类型、不含值。
2. **配置结点**：`pipeConfigParamNode` 只放九类枚举字段（各带 `= 默认值`）——**默认值即常规管线**，非常规管线只在建管线处写非默认列（`pipeConfigParamNode{ .depthType = … }`），这也是「同一事实只写一处」的落点。
3. **译入**：`pipeConfigNode` 里的私有 `createPrimitive` / `createRaster` / `createDepth` / … 各持一个 `switch` 把枚举译成 Vk 字段值，`default` 分支 `Log::printError("…未写预设处理：值 " + std::to_string(static_cast<int>(…)))`。**读值只看这些 switch**。
4. **装配与每管线结点**：`createPipeConfigNode(param, 运行期实参…)` 按配置装配成品（正交类在装配时叠加：`biasId` → 光栅化、`stencilId` → 深度模板、`writeMaskId`/`logicOpId` → 混合；成品子结点始终五个）；每条管线另有 `pipeXxxNode` 捆自己的 descriptor 集合与 mesh，9 条管线的建管线调用在 `VkList.h` 的 `procPipelineNode` 构造里显式写 9 行。

## 二、设计判据（为什么是这些预设，而不是全套 Vk 枚举）

1. **有消费它的着色阶段 / 渲染流程**：状态要被真正读取才有意义——没有消费者就是死预设。
2. **不能被更基本预设等价替代**：能被别的拓扑 + 索引/退化顶点替代的（如 `triangleFan`）不单列。
3. **属管线语义而非材料/技法参数**：常量混合因子（`CONSTANT_*`）、双源因子（`*_SRC1_*`）属材料参数，模板引用值属逐绘制参数——都不固化成预设。
4. **不与同表其它项语义重复**（spec 级冗余）：同一效果被两条以上表达出来的，只留一条。

### 已进枚举（候选池：暂无使用者，但消费者一到位即可用）

| 候选 | 判据 | 说明 |
|---|---|---|
| `lineListWithAdjacency` 等 4 个 | ① | 需几何着色阶段；本引擎管线模型（vert+frag / task+mesh+frag）暂无 → 留着占位，将来加 GS 直接用 |
| `patchList` | ① | 需曲面细分着色阶段；同上 |
| `triangleFan` | ② | 可被 `triangleStrip` + 退化索引替代（D3D/Metal 无此概念）→ 留作 GL 移植对照 |
| `fill/line/point_front_and_back` 3 个 | ①③ | 全剔的消费者是「只走顶点阶段 / 双向薄片」类流程 |
| `point_*` 的 7 种剔除/绕序组合 | ②③ | 点渲染走 `pointList` 拓扑更省；成对留着便于对照 `fill_*`/`line_*` |
| `fill_back_ccw_clampDepth` | ①③ | 需 `depthClamp` feature（本机支持）；深度精度不足/大幅近平面时防穿透 |
| `discardAll` | ① | `rasterizerDiscardEnable=true`：只走顶点/网格阶段（只写时间戳、纯测性能） |

### 仍被剪掉（附判据）

| 剪掉的 | 判据 | 理由 |
|---|---|---|
| `depth test = FALSE` 的 15 种组合 | ④ | spec：`depthTestEnable=VK_FALSE` 时写入恒关闭、比较也不参与 ⇒ 全部塌缩为 `noDepth` |
| `test_noWrite_never` | ④ | 与 `test_never` 完全等价（NEVER ⇒ 无片元通过 ⇒ 写位无意义） |
| blend 的 `*_SRC1_*` | ①③ | 双源混合需 `dualSrcBlend`，属 OIT/形态类技法 |
| blend 的 `CONSTANT_*` | ③ | 常量因子是材料参数，应由材质传 `blendConstants` |
| blend 的 `enable=false` 冗余组合 | ④ | 因子与运算被忽略 ⇒ 等价 `opaque` |
| `logicOpId` 的其余 12 种位运算 | ①③ | 逻辑运算只在「不走混合公式」的特殊通道用（覆盖/取反/异或足够），其余属特技 |
| dynamic 的单设 `viewport`/`scissor`、`*_WITH_COUNT` 族 | ①④ | 视口与裁剪计数必须成对；单视口渲染不需要 count 变体 |

### 保留但必须标注依赖

| 预设 | 依赖/占位说明 |
|---|---|
| `blendId::opaque` 的 6 个因子 | `blendEnable=false` ⇒ 因子与运算被忽略（占位） |
| `depthId::noDepth` 的 compareOp | 测试关 ⇒ 被忽略（占位）；且**模板只走 passOp**，`depthFailOp` 永不触发 |
| `depthId::test_never` | NEVER ⇒ 一律走模板 `depthFailOp`，是「强制深度失败分支」的开关（服务 `stencilId::zFail`） |
| `depthId::test_*_bounds` | 需 `depthBounds` feature；静态边界 (0,1) 是空操作 ⇒ 必须配 `dynamicId::viewportScissorBounds` 在运行时设值 |
| `dynamicId::viewportScissorLineWidth` | 仅 `line_*` 光栅预设有效 |
| `dynamicId::viewportScissorDepthBias` | 仅 `biasId != none` 有效 |
| `dynamicId::viewportScissorRasterDepth` / `All` | **会让所在管线的光栅/深度静态值在运行时被覆盖**，审计日志对这类管线追加 `[动态覆盖 N 项…]` 标记 |
| `rasterId` 的 `line_*` / `point_*` | 需 `fillModeNonSolid`（本机支持） |
| `rasterId` 的 `*_front_and_back` | 绕序（`frontFace`）被忽略，仅 `gl_FrontFacing` 仍有意义 |
| `rasterId::discardAll` | 光栅化被丢弃 ⇒ `polygonMode`/`cullMode`/`frontFace` 均为占位 |
| `writeMaskId::none` | 颜色不写入 ⇒ 该管线的颜色附件仅供深度/模板流程（占位） |
| `logicOpId::*`（除 `disable`） | 需 `logicOp` feature；且与 `blendEnable=true` 互斥（spec 不让同时用） |
| `biasId::polygonOffset` / `shadowOffset` | 偏移量写死在预设结点里；当前 9 条管线沿用历史行为（全部用 `polygonOffset` = 常量 1.0 / 斜率 1.0） |

### 反向陷阱：成对看似等价的预设不要剪

`fill_front_cw` 与 `fill_back_ccw` 之类成对组合，**存活的三角形集合相同**，但 `frontFace` 决定 `gl_FrontFacing`（片元着色器双面光照/法线翻转）与模板正反面语义 ⇒ 各光栅预设互不等价。同理 `polygonMode` 只影响最终光栅化，**剔除发生在它之前**（Khronos 原文：a polygon is clipped and possibly culled before these modes are applied），所以 `line_*` / `point_*` 的剔除与绕序维度也有效。

## 五、维护规则

1. **加一个预设**：在 `VkEnum.h` 对应枚举里加一项（放在语义分组内，行序无所谓，但会决定枚举值）→ 在 `pipeConfigNode` 里对应的私有 `createXxx` 的 `switch` 加一个 `case` → 编译 + 看审计日志。**不需要改别处**（已无预设表要跟）。
2. **改预设**：只改 `createXxxNode` 里那个 `case`；改完用 dev-only 的**管线配置审计日志**（每条管线一行，16 列数值 + 动态覆盖标记）与改前逐行比对。
3. **新增一类预设**：`VkEnum.h` 加 `xxxId` → `pipeConfigParamNode` 加一个字段（带 `= 默认值`）→ `pipeConfigNode` 加一个私有 `createXxx(枚举)` 并把成品接到对应 Vk 结构体（若其字段属某个已有 Vk 结构体，就在那个成品里叠加，**别造第六个成品子结点**）→ `createPipeConfigNode` 里加一行调用。
4. **模板与深度耦合**：`stencilTestEnable=TRUE` 时，深度的通过/失败决定模板走 `passOp` 还是 `depthFailOp`；`noDepth` ⇒ 一律 `passOp`；`test_never` ⇒ 一律 `depthFailOp`；`zPass`/`zFail` 必须开深度测试。
5. **动态状态会覆盖静态值**：`dynamicId` 里声明了某类状态为动态，则该管线的对应静态配置值在运行时被命令缓冲覆盖；审计日志用 `[动态覆盖 N 项…]` 标记这类管线，看日志时别把静态值当成生效值。
6. **候选池项没有使用者是正常的**：枚举里已备好消费者（几何/细分/深度夹紧/逻辑运算）到位后要用的项，使用者列显示 `—`。
